\begin{abstract}
Private inference of Transformer and Large Language Models (LLMs) via Secure Multi-Party Computation (MPC) faces a systems bottleneck: CrypTen-family frameworks execute secret-shared protocols over $\Zring$ via eager, operator-by-operator dispatch in PyTorch. While recent algorithmic advances---Wavelet-encoded Look-Up Tables (CuRL), piecewise low-degree polynomials (PUMA, Nimbus), 1-round Fourier-series activations and ODE Softmax (SHAFT), and hybrid plaintext evaluators (Fission)---substantially reduce the cost of nonlinearities, their reference implementations are spread across separate codebases and pay kernel-launch and host-side dispatch overhead on every elementary ring operation.

We present \textbf{PriX}, an open-source JAX/XLA framework for private Transformer inference that implements five MPC approximation paradigms (\textbf{CrypTen}, \textbf{PUMA/Nimbus piecewise polynomials}, \textbf{SHAFT}, \textbf{CuRL}, and \textbf{Fission}) under a single API while compiling local ring operations into fused XLA kernels. PriX combines (1)~\emph{exact limb-decomposed FP64 matrix multiplication} over $\Zring$ that computes only the limb products surviving modulo $2^{64}$ (6 products with 22-bit limbs for contraction size $K \le 512$, 10 products with 16-bit limbs otherwise); (2)~\emph{\texttt{@jax.jit} fusion} of the local steps of multi-round MPC circuits (carry-lookahead comparison rounds, wavelet LUT gathers, Fourier-series combinations); and (3)~\emph{a shared-memory collective} that exchanges batched openings in a single buffer. Across 10 MPC primitives and 5 Transformer blocks (\texttt{BertTiny}, \texttt{BertBase}, \texttt{GPT2}, \texttt{Llama}, \texttt{ModernBert}), PriX has lower latency than the PyTorch CrypTen baseline in every configuration measured: all 75 on a CPU (five modes) and all 60 on an NVIDIA Tesla T4 GPU (four modes). Transformer-block speedups are \textbf{2.83$\times$--9.20$\times$} on CPU and \textbf{1.97$\times$--3.09$\times$} on GPU. Both frameworks run on a single host, so these measurements reflect computation and inter-process overhead rather than wide-area network cost.
\end{abstract}

%======================================================================
\section{Introduction}
\label{sec:intro}
%======================================================================

Deploying Transformer-based Large Language Models (LLMs)~\cite{vaswani2017attention} on sensitive user prompts or proprietary model weights requires cryptographic privacy guarantees. Secure Multi-Party Computation (MPC) over the machine ring $\Zring$~\cite{mohassel2017secureml,rathee2020cryptflow2,knott2021crypten,hao2022iron} enables two or more distrusting parties to jointly evaluate neural networks on secret-shared inputs without revealing either the client's prompt or the server's parameters.

Over the past five years, CrypTen~\cite{knott2021crypten} has served as the foundational Python research platform for machine-learning-oriented MPC. Building upon CrypTen, a wave of recent cryptographic protocol innovations has dramatically improved the accuracy and round complexity of Transformer nonlinearities ($\operatorname{GeLU}$, $\operatorname{SiLU}$, $\operatorname{Softmax}$, $\operatorname{LayerNorm}$, $\operatorname{RMSNorm}$):
\begin{itemize}
    \item \textbf{Wavelet Approximations and CuRL}~\cite{gouert2024ripple,reis2025wave,santos2024curl}: Wavelet-based cryptographic function approximation---pioneered across Fully Homomorphic Encryption in \textbf{Ripple}~\cite{gouert2024ripple}, mixed-mode MPC in \textbf{Wave Hello to Privacy}~\cite{reis2025wave}, and private LLM evaluation in \textbf{CuRL}~\cite{santos2024curl}---compresses lookup tables via Haar and Biorthogonal-2.2 wavelet transforms paired with probabilistic truncation ($\mathsf{TruncPr}$)~\cite{escudero2020improved}, substantially reducing LUT communication and memory footprints while preserving high numerical fidelity.
    \item \textbf{SHAFT}~\cite{kei2025shaft} introduced 1-round trigonometric-triple Fourier-series evaluation for $\operatorname{GeLU}$, $\operatorname{SiLU}$, $\operatorname{Erf}$, $\operatorname{Sigmoid}$, and $\operatorname{Tanh}$, alongside a constant-round Forward-Euler Ordinary Differential Equation (ODE) solver for $\operatorname{Softmax}$.
    \item \textbf{Fission}~\cite{ugurbil2025fission} introduced a hybrid permute-and-reveal architecture that offloads elementwise nonlinearities to a non-colluding plaintext evaluator party.
    \item \textbf{PUMA}~\cite{dong2023puma} and \textbf{Nimbus}~\cite{li2024nimbus} replace $\operatorname{GeLU}$, $\operatorname{SiLU}$, and $\exp$ with piecewise low-degree polynomials guarded by one or two secure comparisons, avoiding lookup tables entirely; Nimbus additionally fits the pieces to the observed input distributions of Transformer activations.
\end{itemize}

Despite these algorithmic advances, MPC research for Transformers faces two systems obstacles:
\begin{enumerate}
    \item \textbf{Ecosystem Fragmentation:} The original CrypTen repository is no longer actively developed, and CuRL, SHAFT, and Fission live in separate CrypTen forks (PUMA lives in SecretFlow SPU), each of which needs compatibility patches to run on current Python, PyTorch, and JAX releases. Researchers conducting ablations across approximation paradigms must port models between distinct codebases.
    \item \textbf{Eager Dispatch Overhead:} In eager PyTorch, every elementary bitwise shift, mask, and ring addition in an MPC circuit is a separate CPU or CUDA kernel launch with host-side Python control flow in between. A single 64-bit carry-lookahead comparison~\cite{kogge1973parallel} executes 6 tree rounds of bitwise XOR and AND operations, so its local work is split into many tiny launches. In addition, because neither CPUs' BLAS libraries nor CUDA provide 64-bit integer (\texttt{int64}) GEMM, CrypTen's CUDA backend splits each operand into 3 (for contraction size $K < 256$) or 4 limbs and computes all $9$ or $16$ pairwise limb products in one batched FP64 \texttt{torch.matmul}, discarding the products that vanish modulo $2^{64}$ only afterwards; on CPU it falls back to PyTorch's unblocked \texttt{int64} matmul.
\end{enumerate}

To address both challenges, we design and implement \textbf{PriX} (\emph{Private Accelerated Transformers in JAX}), a modern, drop-in alternative to CrypTen built on the JAX/XLA compiler stack~\cite{bradbury2018jax}.

\paragraph{Contributions.} Our contributions are:
\begin{enumerate}
    \item \textbf{A Multi-Paradigm MPC Framework:} PriX implements \textbf{CrypTen} polynomial/Newton--Raphson approximations~\cite{knott2021crypten}, \textbf{PUMA / Nimbus}-style piecewise low-degree polynomials~\cite{dong2023puma,li2024nimbus}, \textbf{SHAFT} Fourier-series and ODE Softmax~\cite{kei2025shaft}, \textbf{CuRL} wavelet LUTs with $\mathsf{TruncPr}$~\cite{santos2024curl,escudero2020improved}, and \textbf{Fission} hybrid evaluators~\cite{ugurbil2025fission} behind a single API on Python~3.10--3.13, tested on CPUs and CUDA GPUs. Researchers switch paradigms in one line (\texttt{mode="lut" | "poly" | "shaft" | "crypten" | "fission"}) or mix methods per function (e.g., SHAFT ODE Softmax with CuRL wavelet LayerNorm).
    \item \textbf{XLA Kernel Fusion for MPC Circuits:} PriX compiles the local (non-communicating) steps of secret-share arithmetic, carry-lookahead comparison rounds, wavelet LUT gathers, and Fourier-series combinations via \texttt{@jax.jit}, removing intermediate memory traffic and Python dispatch between elementary ring operations.
    \item \textbf{Exact Limb-Decomposed $\Zring$ Matrix Multiplication and Low-Overhead Collectives:} PriX computes only the limb products that survive modulo $2^{64}$ (6 instead of CrypTen's 9 for $K < 256$, 6 instead of 16 for $256 \le K \le 512$, and 10 instead of 16 for $K > 512$) inside one compiled kernel, and exchanges batched openings through a shared-memory ring buffer.
    \item \textbf{CPU and GPU Evaluation:} We compare PriX against the PyTorch CrypTen baseline on 10 primitives and 5 Transformer blocks (\texttt{BertTiny}, \texttt{BertBase}, \texttt{GPT2}, \texttt{Llama}, \texttt{ModernBert}) on a CPU (all 5 modes, 75 configurations) and an NVIDIA Tesla T4 GPU (4 modes, 60 configurations). PriX has lower latency in every configuration, with \textbf{2.83$\times$--9.20$\times$} Transformer-block speedups on CPU and \textbf{1.97$\times$--3.09$\times$} on GPU. We also document the limits of these measurements: a single host, different local transports, and few repetitions.
\end{enumerate}

\section{Background and MPC Preliminaries}
\label{sec:background}
%======================================================================

\subsection{Fixed-Point Encoding and Secret Sharing over $\Zring$}
Real-valued tensors $x \in \mathbb{R}^{d_1 \times \dots \times d_k}$ are encoded into the ring $\Zring$ using a fixed-point scaling factor $S = 2^f$ (where $f = 16$ precision bits by default):
\begin{equation}
    \mathsf{Encode}(x) = \lfloor x \cdot 2^f \rceil \bmod 2^{64}, \qquad
    \mathsf{Decode}(\hat{x}) = \frac{\mathsf{Signed}_{64}(\hat{x})}{2^f}.
\end{equation}
Across $N$ parties (typically $N=2$), PriX maintains two secret-sharing representations:
\begin{itemize}
    \item \textbf{Additive Arithmetic Sharing ($\shareA{x}$):} Party $p \in \{0, \dots, N-1\}$ holds $\shareA{x}_p \in \Zring$ such that $\sum_{p=0}^{N-1} \shareA{x}_p \equiv \mathsf{Encode}(x) \pmod{2^{64}}$. Linear combinations $\shareA{x + y} = \shareA{x} + \shareA{y}$ and public multiplications $\shareA{c \cdot x} = c \cdot \shareA{x}$ require zero communication (followed by local or interactive fixed-point truncation).
    \item \textbf{XOR Binary Sharing ($\shareB{x}$):} Party $p$ holds $\shareB{x}_p \in \{0, 1\}^{64}$ such that $\bigoplus_{p=0}^{N-1} \shareB{x}_p = x$. Bitwise XOR ($\oplus$) and bit shifts ($\ll, \gg$) are local; bitwise AND ($\wedge$) requires 1 communication round via binary Beaver triples.
\end{itemize}

\subsection{Multiplication, Truncation, and Nonlinearity Paradigms}
\paragraph{Beaver Multiplication Triples.}
To compute the private product $\shareA{z} = \shareA{x \cdot y}$ (or matrix product $\shareA{X Y}$), the parties consume a pre-generated triple $(\shareA{a}, \shareA{b}, \shareA{c})$ with $c = a \cdot b \bmod 2^{64}$~\cite{beaver1991efficient}. Parties locally compute $\shareA{\epsilon} = \shareA{x} - \shareA{a}$ and $\shareA{\delta} = \shareA{y} - \shareA{b}$, open $(\epsilon, \delta)$ in a single communication round, and evaluate:
\begin{equation}
    \shareA{x \cdot y}_p = \shareA{c}_p + \epsilon \shareA{b}_p + \shareA{a}_p \delta + \mathbb{I}[p = 0] \cdot (\epsilon \delta) \pmod{2^{64}}.
    \label{eq:beaver}
\end{equation}
Because multiplying two $2^f$-scaled integers yields scale $2^{2f}$, the product must be truncated by $f$ bits:
\begin{itemize}
    \item \emph{CrypTen Wrap-Count Truncation (\texttt{crypten}):} Parties locally arithmetic-shift their shares by $f$ bits and correct for unsigned ring wraps $\theta_x$ via a single-round masked wrap-count protocol~\cite{knott2021crypten}.
    \item \emph{Probabilistic Truncation (\texttt{egk}):} Following Escudero et al.~\cite{escudero2020improved} and CuRL~\cite{santos2024curl}, parties mask $\shareA{z}$ with a correlated random pair $(\shareA{r}, \shareA{r \gg f})$, reveal $z + r$, and subtract $\shareA{r \gg f}$ from $(z + r) \gg f$.
\end{itemize}

\paragraph{Five Nonlinear Approximation Backends.}
Table~\ref{tab:modes} summarizes the five approximation modes unified in PriX:
\begin{enumerate}
    \item \textbf{CrypTen Mode (\texttt{mode="crypten"})}~\cite{knott2021crypten}: Approximates $\exp(x) \approx (1 + x / 2^m)^{2^m}$ via $m=8$ repeated squarings, $1/x$ and $1/\sqrt{x}$ via Newton--Raphson iterations, and $\operatorname{GeLU}(x)$ via Taylor-series $\operatorname{erf}(x/\sqrt{2})$.
    \item \textbf{PUMA / Nimbus Piecewise Polynomial Mode (\texttt{mode="poly"})}~\cite{dong2023puma,li2024nimbus}: Evaluates $\operatorname{GeLU}$, $\operatorname{SiLU}$, $\operatorname{Tanh}$, $\operatorname{Sigmoid}$, and $\operatorname{Erf}$ with one batched secure comparison (computing $[\shareA{x} < 0]$ and $[|\shareA{x}| < w]$ in a single carry-lookahead circuit) followed by a degree-4 polynomial on $|x|$, and $\exp$ with a two-piece degree-4 polynomial on $(-5, 0]$ and $[0, 2.5]$ whose pieces share one power basis. No lookup tables are used. The coefficients are least-squares fits over the stated intervals rather than the distribution-aware fits of Nimbus.
    \item \textbf{SHAFT Mode (\texttt{mode="shaft"})}~\cite{kei2025shaft}: Evaluates $\operatorname{GeLU}$, $\operatorname{SiLU}$, $\operatorname{Erf}$, $\operatorname{Sigmoid}$, and $\operatorname{Tanh}$ via a Fourier sine series $\sum_{k=1}^{K} \beta_k \sin(k \omega x)$ in \emph{1 communication round}: parties reveal $\delta = x - t$ against a pre-shared trigonometric triple $(\shareA{t}, \shareA{\sin(k \omega t)}, \shareA{\cos(k \omega t)})$ and apply the angle-addition identity locally:
    \begin{equation}
        \shareA{\sin(k \omega x)} = \sin(k \omega \delta)\shareA{\cos(k \omega t)} + \cos(k \omega \delta)\shareA{\sin(k \omega t)}.
        \label{eq:shaft_trig}
    \end{equation}
    For $\operatorname{Softmax}$, SHAFT integrates the differential equation $y'(t) = y(t) \odot (x - \langle y(t), x \rangle)$ over $t \in [0, 1]$ using a fixed number of Forward-Euler steps, without any division, reciprocal, or secure $\max$.
    \item \textbf{CuRL Wavelet LUT Mode (\texttt{mode="lut"})}~\cite{santos2024curl}: Builds on wavelet-based function approximation~\cite{gouert2024ripple,reis2025wave}: lookup tables are compressed with Haar and Biorthogonal-2.2 wavelet transforms into coarse coefficient tables, secret-shared lookups are evaluated with one-hot correlated randomness~\cite{santos2024curl}, and Biorthogonal-2.2 tables are interpolated piecewise-linearly after probabilistic truncation $\mathsf{TruncPr}$~\cite{escudero2020improved}.
    \item \textbf{Fission Evaluator Mode (\texttt{mode="fission"})}~\cite{ugurbil2025fission}: Masks and randomly permutes shares before revealing them to a non-colluding plaintext evaluator party, which computes exact float32 nonlinearities and returns fresh secret shares. The evaluator learns the permuted plaintext values, so the security argument relies on the evaluator not colluding with the MPC parties and on partitioning values across evaluators~\cite{ugurbil2025fission}.
\end{enumerate}

\subsection{Exact Limb-Decomposed FP64 Matrix Multiplication over $\Zring$}
\label{sec:limb_matmul}
Neither CPU BLAS libraries nor cuBLAS provide 64-bit integer (\texttt{int64}) GEMM, so PyTorch's \texttt{int64} matmul runs on generic unblocked loops. Double-precision GEMM, by contrast, is available in optimized form on both (AVX/FMA on CPU, \texttt{cublasDgemm} on GPU). Note that on the Tesla T4 used in our GPU experiments, FP64 throughput is a small fraction of FP32 throughput and does not use tensor cores.

To compute $C = A B \bmod 2^{64}$ for $A \in \Zring^{M \times K}$ and $B \in \Zring^{K \times N}$ exactly in FP64, we split each unsigned 64-bit entry into $L$ limbs of $w$ bits, $A = \sum_{i} A_i 2^{wi}$ and $B = \sum_j B_j 2^{wj}$. Because only the result modulo $2^{64}$ is needed, every limb pair with $(i + j)\,w \ge 64$ contributes a multiple of $2^{64}$ and can be skipped:
\begin{equation}
    A B \equiv \sum_{(i + j)\,w < 64} (A_i B_j) \, 2^{w(i + j)} \pmod{2^{64}}.
    \label{eq:ten_limbs}
\end{equation}
PriX uses two limb configurations, chosen by the contraction size $K$:
\begin{itemize}
    \item $K \le 512$: $L = 3$ limbs of $w = 22$ bits ($A_2, B_2$ have 20 bits), so only the \textbf{6} pairs with $i + j \le 2$ are computed. Each product entry is below $K \cdot 2^{44} \le 2^{53}$, so every FP64 GEMM is exact.
    \item $K > 512$: $L = 4$ limbs of $w = 16$ bits, so only the \textbf{10} pairs with $i + j \le 3$ are computed. On GPU each pair is a separate slice of one batched GEMM. Each pair product is converted to \texttt{uint64} individually, which is exact for $K \cdot 2^{32} \le 2^{53}$, i.e.\ $K \le 2^{21}$. On CPU, each pair product is likewise converted to \texttt{uint64} before products of equal shift are added, so both backends share the same $K \le 2^{21}$ bound.
    \item $K > 2^{21}$: the contraction is split into chunks of at most $2^{21}$. Each chunk is multiplied exactly as above, and the \texttt{uint64} partial results are added; wrap-around addition is exact modulo $2^{64}$, so the result is bit-exact for any $K$. The chunking is decided at trace time, so it adds no overhead when $K \le 2^{21}$.
\end{itemize}
CrypTen's CUDA backend~\cite{knott2021crypten} uses 3 limbs for $K < 256$ and 4 limbs otherwise, and computes \emph{all} $9$ or $16$ limb products in one batched \texttt{torch.matmul} before discarding the vanishing ones. PriX therefore performs 6 instead of 9 GEMMs for $K < 256$, 6 instead of 16 for $256 \le K \le 512$, and 10 instead of 16 for $K > 512$. On GPU, PriX stacks the surviving limb pairs into one batched GEMM, and the limb extraction, GEMM, conversion, shifts, and modular accumulation are compiled together with the Beaver combination $\shareA{C} + \epsilon \shareA{B} + \shareA{A}\delta + \mathbb{I}[p=0](\epsilon\delta)$. On CPU, CrypTen uses PyTorch's \texttt{int64} matmul directly, so PriX's advantage there comes mainly from using FP64 BLAS.

\subsection{Compiled Set-Propagate-Kill Comparison Circuits}
\label{sec:koggestone}
Private comparisons ($\shareA{x} < 0$, $\operatorname{ReLU}$, $\operatorname{Max}$) extract the most significant bit of a secret-shared ring element by converting $\shareA{x}$ into binary shares with a parallel-prefix carry-lookahead circuit. Like CrypTen, PriX uses the Set-Propagate-Kill (SPK) tree of Damgård et al., a Kogge--Stone-style prefix circuit~\cite{kogge1973parallel} with $\log_2 64 = 6$ rounds. In round $r$ with stride $s = 2^r$, the set and propagate bit-vectors are updated as
\begin{equation}
    S^{(r+1)} = S^{(r)} \oplus \big(P^{(r)} \wedge (S^{(r)} \ll s)\big), \qquad
    P^{(r+1)} = P^{(r)} \wedge (P^{(r)} \ll s),
\end{equation}
where XOR can replace OR because the two terms are never both set. As in CrypTen, both AND gates of a round are opened in one batched binary-Beaver exchange. PriX differs in how the local work is executed:
\begin{itemize}
    \item The dealer generates the binary triples for all 6 rounds in one call (\texttt{generate\_spk\_triples}) instead of one call per round.
    \item The local work between two consecutive openings---applying the previous round's Beaver correction, masking, shifting, and preparing the next round's masked operands---is one compiled kernel (\texttt{\_spk\_step\_fused} in \texttt{circuit.py}). The first and last rounds are fused with the arithmetic-to-binary conversion and with the binary-to-arithmetic conversion of the sign bit, respectively (\texttt{\_a2b\_post\_and\_spk\_round0\_pre}, \texttt{\_spk\_round\_last\_and\_ltz\_b2a\_pre}, \texttt{\_b2a\_combine}).
\end{itemize}

\subsection{Compiled Wavelet LUT Evaluation and Fourier Combination}
\label{sec:lut_shaft_fusion}
In CuRL mode (\texttt{mode="lut"}), a nonlinearity such as $\operatorname{InvSqrt}$, $\operatorname{Exp}$, $\operatorname{GeLU}$, or $\operatorname{SiLU}$ truncates the secret input to a table index, reveals the index masked by a one-hot correlation, rotates the one-hot share accordingly, and takes its dot product with the (Biorthogonal-2.2) coefficient tables before interpolating. In PriX:
\begin{itemize}
    \item All wavelet tables are built once and placed on the accelerator at initialization (\texttt{LookupTables(device)}).
    \item The rotation and dot product against one table, or against the two Biorthogonal-2.2 tables used for interpolation, are one compiled kernel (\texttt{\_lut\_gather\_dot}, \texttt{\_bior\_lut\_gather\_dot} in \texttt{array.py}).
    \item In SHAFT mode, after the single opening of $\delta = x - t$, the evaluation of Equation~\ref{eq:shaft_trig} for all $K$ terms---computing $\sin(k\omega\delta)$ and $\cos(k\omega\delta)$, scaling them by $\beta_k$, multiplying against the triple shares, and summing---is one compiled kernel (\texttt{\_fourier\_linear\_comb\_jit} in \texttt{approximations.py}).
\end{itemize}

\subsection{Batched Openings and Shared-Memory Collectives}
\label{sec:collectives}
Every private multiplication opens two masked tensors, $\epsilon = x - a$ and $\delta = y - b$. As in CrypTen, both are opened in one round. When $\epsilon$ and $\delta$ have different shapes (e.g.\ $\epsilon \in \Zring^{M \times K}$ and $\delta \in \Zring^{K \times N}$ in a matrix multiplication), PriX flattens and concatenates them on the device in a compiled kernel, copies the result to the host as a single buffer, exchanges it, and splits the result on the device.

For multi-process execution on one host, \texttt{InProcessCommunicator} uses a \textbf{4-slot shared-memory ring buffer} (\texttt{multiprocessing.RawArray}) with a 1-byte pipe message as the readiness signal. Each party writes its buffer into slot $\text{step} \bmod 4$, sends the slot index over the pipe, and adds its peer's slot directly from shared memory, without pickling tensors through queues. CrypTen instead uses \texttt{torch.distributed} with the \texttt{gloo} backend over loopback TCP. This difference affects every opening, so part of the end-to-end speedups in Section~\ref{sec:evaluation} is due to the communicator rather than to kernel fusion; we do not separate the two effects in this report.

\section{Researcher Ergonomics and Unified API}
\label{sec:api}
%======================================================================

A central design goal of PriX is enabling cryptography and machine learning researchers to prototype and benchmark private Transformer protocols with minimal boilerplate. Listing~\ref{lst:quickstart} shows a multi-party ablation that evaluates a pre-norm Transformer block under all five approximation modes.

\begin{lstlisting}[style=pythonstyle, caption={Evaluating a private Transformer block under all five MPC approximation modes in PriX.}, label={lst:quickstart}]
import numpy as np
import prix
import prix.nn as nn

class TransformerBlock(nn.Module):
    def __init__(self, d_model=64, n_heads=4, d_ff=256):
        super().__init__()
        self.ln1 = nn.LayerNorm(d_model)
        self.attn = nn.MultiheadAttention(d_model, n_heads)
        self.ln2 = nn.LayerNorm(d_model)
        self.ffn = nn.Sequential(nn.Linear(d_model, d_ff), nn.GELU(), nn.Linear(d_ff, d_model))

    def forward(self, x):
        h = self.ln1(x)
        x = x + self.attn(h, h, h)
        return x + self.ffn(self.ln2(x))

def evaluate_private_block(tokens):
    # Party 0 secret-shares the model weights; party 1 secret-shares the token embeddings
    model = TransformerBlock().encrypt(src=0)
    x = prix.array(tokens, src=1)
    return model(x).reconstruct()

tokens = np.random.randn(1, 16, 64).astype(np.float32)
for mode in ["crypten", "poly", "shaft", "lut", "fission"]:
    out = prix.run(evaluate_private_block, tokens, world_size=2, mode=mode)
\end{lstlisting}

\subsection{Experimental Setup}
We compare \textbf{PriX (JAX)} against a PyTorch \textbf{CrypTen} baseline~\cite{knott2021crypten}: the CrypTen fork that serves as the reference implementation of CuRL~\cite{santos2024curl} and Fission~\cite{ugurbil2025fission}. SHAFT's Fourier activations and ODE Softmax~\cite{kei2025shaft}, and the piecewise polynomials of \texttt{poly} mode, are added to this baseline by our benchmark script, which ports PriX's algorithms to it one-to-one (same coefficients, intervals, comparisons, and power-basis sharing). Where PriX seeds Newton--Raphson iterations with the limit approximation of $\exp$ regardless of the configured $\exp$ method, the baseline is configured the same way. Both frameworks run 2-party semi-honest protocols with the Trusted First Party (\texttt{TFP}) dealer, $f = 16$ fractional bits, identical inputs, and identical per-mode configuration files (each mode's YAML merged over the framework's default configuration; the two frameworks' default configurations agree on every parameter used). The five modes are:
\begin{enumerate}
    \item \textbf{CrypTen approximations (\texttt{crypten})}~\cite{knott2021crypten};
    \item \textbf{Piecewise polynomials (\texttt{poly})}~\cite{dong2023puma,li2024nimbus};
    \item \textbf{SHAFT Fourier + ODE (\texttt{shaft})}~\cite{kei2025shaft};
    \item \textbf{CuRL wavelet LUTs with $\mathsf{TruncPr}$ (\texttt{lut})}~\cite{santos2024curl}; and
    \item \textbf{Fission hybrid evaluator (\texttt{fission})}~\cite{ugurbil2025fission}, with one evaluator process.
\end{enumerate}
We benchmark 10 MPC primitives and nonlinearities ($\text{MatMul } 128\times 128$, $\text{Mul } 128\times 128$, $\text{ReLU } 32\times 64$, $\text{Exp } 32\times 64$, $\text{Reciprocal } 32\times 64$, $\text{InvSqrt } 32\times 64$, $\text{GeLU } 32\times 64$, $\text{SiLU } 32\times 64$, $\text{Softmax } 4\times 32\times 32$, $\text{LayerNorm } 4\times 32\times 64$) and 5 Transformer configurations with sequence length $L=16$: \texttt{BertTiny} (2 blocks, $d=128$, $H=2$), \texttt{BertBase} (1 block, $d=768$, $H=12$), \texttt{GPT2} (1 block, $d=768$, $H=12$), \texttt{Llama} (1 block, $d=768$, RoPE + SwiGLU + RMSNorm, grouped-query attention), and \texttt{ModernBert} (1 block, $d=768$, $H=12$, RoPE + GeGLU). Weights and inputs are random; we measure latency only, not model accuracy.

\paragraph{Methodology.} All parties run as separate processes on one host and communicate through each framework's own local transport (Section~\ref{sec:collectives}); no network latency or bandwidth limit is emulated, and we do not report communication volume. Each primitive is run 2 times untimed (to exclude JIT compilation and cache warmup) and then timed 5 times; each Transformer block is warmed up once and timed 3 times. Parties synchronize with a barrier before every timed run, device work is synchronized before the timer stops, and we report the median. Within a platform, all reported modes of both frameworks were measured in a single session (all five modes on CPU, and four modes on GPU, where \texttt{poly} results are pending). CPU experiments use the host listed in Table~\ref{tab:cpu_llm}'s caption. GPU experiments use a Google Colab instance with one NVIDIA Tesla T4. With so few repetitions, differences of roughly 10\% or less between the two frameworks should be treated as within run-to-run noise.

\end{itemize}

\section{Security Considerations and Limitations}
\label{sec:security}
%======================================================================

PriX is a research framework operating in the \textbf{semi-honest (honest-but-curious)} model, and its current implementation has the following limitations:
\begin{enumerate}
    \item \textbf{Correlated Randomness Providers (\texttt{TFP} vs.\ \texttt{TTP}):} Like CrypTen~\cite{knott2021crypten}, PriX defaults to the Trusted First Party (\texttt{TFP}) provider, in which Party~0 generates the Beaver triples, truncation pairs, and LUT correlations. Party~0 therefore knows the dealer randomness and can recover every secret; \texttt{TFP} is suitable only for performance measurement, and all experiments in this report use it for both frameworks. Setting \texttt{cfg.mpc.provider = "TTP"} runs a separate dealer process (\texttt{TTPServer}) under the usual non-colluding third-party assumption.
    \item \textbf{Pseudorandom Number Generation:} Correlated randomness is currently expanded with \texttt{SplitMix64} (inside compiled kernels) and \texttt{PCG64} (on the host), seeded from OS entropy exchanged at initialization. Neither generator is a cryptographically secure PRF, so a party that observes part of a stream may predict the rest. Replacing them with a keyed counter-mode PRF (e.g.\ Threefry or AES-CTR) is required before PriX can protect real data.
    \item \textbf{Probabilistic Truncation Range:} PriX's $\mathsf{TruncPr}$~\cite{escudero2020improved} is instantiated with parameter $\ell = 62$ in $\Zring$: the opened value is $2^{64-\ell-1}(x + 2^{\ell-1} + r)$ with a uniform $\ell$-bit mask $r$ and a masked carry bit, which hides $x$ perfectly provided the ring integer satisfies $|x| < 2^{\ell-1} = 2^{61}$. With $f = 16$, this means real values below $2^{29}$ in magnitude for products at precision $2f$, and below $2^{45}$ for values at precision $f$. Values outside this range give incorrect results. As usual, the truncated result may be off by one unit in the last place.
    \item \textbf{Evaluation Scope:} All measurements are single-host, with no network emulation and no reported communication volume; they characterize computation and local inter-process overhead, not wide-area deployment. The two frameworks also use different local transports (Section~\ref{sec:collectives}). Model accuracy under each approximation mode is not evaluated here. PriX has been tested on CPUs and CUDA GPUs only. On TPUs, its FP64 limb matrix multiplication would rely on emulated double precision.
\end{enumerate}

%======================================================================
\section{Conclusion}
\label{sec:conclusion}
%======================================================================

We presented \textbf{PriX}, a JAX/XLA framework for privacy-preserving Transformer research via Secure Multi-Party Computation. PriX implements five MPC approximation paradigms (\textbf{CrypTen}, \textbf{piecewise polynomials}, \textbf{SHAFT}, \textbf{CuRL}, and \textbf{Fission}) behind one API. It compiles the local steps of each protocol with XLA, computes only the surviving limb products in its exact FP64 ring matrix multiplication, and uses a shared-memory local transport. On a single host, it has lower latency than the PyTorch CrypTen baseline in every configuration we measured, with Transformer-block speedups of \textbf{2.83$\times$--9.20$\times$} on CPU and \textbf{1.97$\times$--3.09$\times$} on a Tesla T4 GPU. Separating the effects of kernel fusion and transport, evaluating over real networks, reporting communication volume and accuracy, and replacing the non-cryptographic PRNGs are the main next steps. PriX is open-source and available on PyPI via \texttt{pip install prix-jax}.
