\begin{abstract}
Private inference of Transformer and Large Language Models (LLMs) via Secure Multi-Party Computation (MPC) faces a systems bottleneck: CrypTen-family frameworks execute secret-shared protocols over $\Zring$ via eager, operator-by-operator dispatch in PyTorch. While recent algorithmic advances---Wavelet-encoded Look-Up Tables (Curl), piecewise low-degree polynomials (PUMA, Nimbus), 1-round Fourier-series activations and ODE Softmax (SHAFT), and hybrid plaintext evaluators (Fission)---substantially reduce the cost of nonlinearities, their reference implementations are spread across separate codebases and pay kernel-launch and host-side dispatch overhead on every elementary ring operation.

We present \textbf{PriX}, an open-source JAX/XLA framework for private Transformer inference that implements five MPC approximation paradigms (\textbf{CrypTen}, \textbf{PUMA/Nimbus piecewise polynomials}, \textbf{SHAFT}, \textbf{Curl}, and \textbf{Fission}) under a single API while compiling local ring operations into fused XLA kernels. PriX combines (1)~\emph{exact limb-decomposed FP64 matrix multiplication} over $\Zring$ that computes only the limb products surviving modulo $2^{64}$ (6 products with 22-bit limbs for contraction size $K \le 512$, 10 products with 16-bit limbs otherwise); (2)~\emph{\texttt{@jax.jit} fusion} of the local steps of multi-round MPC circuits (carry-lookahead comparison rounds, wavelet LUT gathers, Fourier-series combinations); and (3)~\emph{a shared-memory collective} that exchanges batched openings in a single buffer. Across 10 MPC primitives and 5 Transformer blocks (\texttt{BertTiny}, \texttt{BertBase}, \texttt{GPT2}, \texttt{Llama}, \texttt{ModernBert}) in all five modes, PriX has lower latency than the PyTorch CrypTen baseline in all 75 configurations on both a CPU and an NVIDIA Tesla T4 GPU. Transformer-block speedups are \textbf{2.83$\times$--9.20$\times$} on CPU and \textbf{1.98$\times$--3.18$\times$} on GPU. A transport ablation shows that most of this is not due to PriX's faster local transport: with CrypTen's \texttt{gloo}/TCP transport, PriX is still 3.24$\times$ faster on Transformer blocks (geometric mean, CPU). Both frameworks run on a single host, so these measurements reflect computation and inter-process overhead rather than wide-area network cost.
\end{abstract}

%======================================================================
\section{Introduction}
\label{sec:intro}
%======================================================================

Deploying Transformer-based Large Language Models (LLMs)~\cite{vaswani2017attention} on sensitive user prompts or proprietary model weights requires cryptographic privacy guarantees. Secure Multi-Party Computation (MPC) over the machine ring $\Zring$~\cite{mohassel2017secureml,rathee2020cryptflow2,knott2021crypten,hao2022iron} enables two or more distrusting parties to jointly evaluate neural networks on secret-shared inputs without revealing either the client's prompt or the server's parameters.

Over the past five years, CrypTen~\cite{knott2021crypten} has served as the foundational Python research platform for machine-learning-oriented MPC. Building upon CrypTen, a wave of recent cryptographic protocol innovations has dramatically improved the accuracy and round complexity of Transformer nonlinearities ($\operatorname{GeLU}$, $\operatorname{SiLU}$, $\operatorname{Softmax}$, $\operatorname{LayerNorm}$, $\operatorname{RMSNorm}$):
\begin{itemize}
    \item \textbf{Wavelet Approximations and Curl}~\cite{gouert2024ripple,reis2025wave,santos2024curl}: Wavelet-based cryptographic function approximation---pioneered across Fully Homomorphic Encryption in \textbf{Ripple}~\cite{gouert2024ripple}, mixed-mode MPC in \textbf{Wave Hello to Privacy}~\cite{reis2025wave}, and private LLM evaluation in \textbf{Curl}~\cite{santos2024curl}---compresses lookup tables via Haar and Biorthogonal-2.2 wavelet transforms paired with probabilistic truncation ($\mathsf{TruncPr}$)~\cite{escudero2020improved}, substantially reducing LUT communication and memory footprints while preserving high numerical fidelity.
    \item \textbf{SHAFT}~\cite{kei2025shaft} introduced 1-round trigonometric-triple Fourier-series evaluation for $\operatorname{GeLU}$, $\operatorname{SiLU}$, $\operatorname{Erf}$, $\operatorname{Sigmoid}$, and $\operatorname{Tanh}$, alongside a constant-round Forward-Euler Ordinary Differential Equation (ODE) solver for $\operatorname{Softmax}$.
    \item \textbf{Fission}~\cite{ugurbil2025fission} introduced a hybrid permute-and-reveal architecture that offloads elementwise nonlinearities to a non-colluding plaintext evaluator party.
    \item \textbf{PUMA}~\cite{dong2023puma} and \textbf{Nimbus}~\cite{li2024nimbus} replace $\operatorname{GeLU}$, $\operatorname{SiLU}$, and $\exp$ with piecewise low-degree polynomials guarded by one or two secure comparisons, avoiding lookup tables entirely; Nimbus additionally fits the pieces to the observed input distributions of Transformer activations.
\end{itemize}

Despite these algorithmic advances, MPC research for Transformers faces two systems obstacles:
\begin{enumerate}
    \item \textbf{Ecosystem Fragmentation:} The original CrypTen repository was archived in May 2025, and Curl, SHAFT, and Fission live in separate CrypTen forks (PUMA lives in SecretFlow SPU), each of which needs compatibility patches to run on current Python, PyTorch, and JAX releases. Researchers conducting ablations across approximation paradigms must port models between distinct codebases.
    \item \textbf{Eager Dispatch Overhead:} In eager PyTorch, every elementary bitwise shift, mask, and ring addition in an MPC circuit is a separate CPU or CUDA kernel launch with host-side Python control flow in between. A single 64-bit carry-lookahead comparison~\cite{kogge1973parallel} executes 6 tree rounds of bitwise XOR and AND operations, so its local work is split into many tiny launches. In addition, because neither CPUs' BLAS libraries nor CUDA provide 64-bit integer (\texttt{int64}) GEMM, CrypTen's CUDA backend splits each operand into 3 (for contraction size $K < 256$) or 4 limbs and computes all $9$ or $16$ pairwise limb products in one batched FP64 \texttt{torch.matmul}, discarding the products that vanish modulo $2^{64}$ only afterwards; on CPU it falls back to PyTorch's unblocked \texttt{int64} matmul.
\end{enumerate}

To address both challenges, we design and implement \textbf{PriX} (\emph{Private Accelerated Transformers in JAX}), a modern, drop-in alternative to CrypTen built on the JAX/XLA compiler stack~\cite{bradbury2018jax}.

\paragraph{Contributions.} Our contributions are:
\begin{enumerate}
    \item \textbf{A Multi-Paradigm MPC Framework:} PriX implements \textbf{CrypTen} polynomial/Newton--Raphson approximations~\cite{knott2021crypten}, \textbf{PUMA / Nimbus}-style piecewise low-degree polynomials~\cite{dong2023puma,li2024nimbus}, \textbf{SHAFT} Fourier-series and ODE Softmax~\cite{kei2025shaft}, \textbf{Curl} wavelet LUTs with $\mathsf{TruncPr}$~\cite{santos2024curl,escudero2020improved}, and \textbf{Fission} hybrid evaluators~\cite{ugurbil2025fission} behind a single API on Python~3.10--3.13, tested on CPUs and CUDA GPUs. Researchers switch paradigms in one line (\texttt{mode="lut" | "poly" | "shaft" | "crypten" | "fission"}) or mix methods per function (e.g., SHAFT ODE Softmax with Curl wavelet LayerNorm).
    \item \textbf{XLA Kernel Fusion for MPC Circuits:} PriX compiles the local (non-communicating) steps of secret-share arithmetic, carry-lookahead comparison rounds, wavelet LUT gathers, and Fourier-series combinations via \texttt{@jax.jit}, removing intermediate memory traffic and Python dispatch between elementary ring operations.
    \item \textbf{Exact Limb-Decomposed $\Zring$ Matrix Multiplication and Low-Overhead Collectives:} PriX computes only the limb products that survive modulo $2^{64}$ (6 instead of CrypTen's 9 for $K < 256$, 6 instead of 16 for $256 \le K \le 512$, and 10 instead of 16 for $K > 512$) inside one compiled kernel, and exchanges batched openings through a shared-memory ring buffer.
    \item \textbf{CPU and GPU Evaluation:} We compare PriX against the PyTorch CrypTen baseline on 10 primitives and 5 Transformer blocks (\texttt{BertTiny}, \texttt{BertBase}, \texttt{GPT2}, \texttt{Llama}, \texttt{ModernBert}) in all 5 modes on a CPU and an NVIDIA Tesla T4 GPU (75 configurations each). PriX has lower latency in every configuration, with \textbf{2.83$\times$--9.20$\times$} Transformer-block speedups on CPU and \textbf{1.98$\times$--3.18$\times$} on GPU. A transport ablation isolates how much of the speedup comes from PriX's shared-memory transport (about 20\% on Transformer blocks, on a log scale), an accuracy sweep reports each mode's error and valid input ranges, and we document the remaining limits of the measurements: a single host, a CPU-only ablation, and few repetitions.
\end{enumerate}

\section{Background and MPC Preliminaries}
\label{sec:background}
%======================================================================

\subsection{Fixed-Point Encoding and Secret Sharing over $\Zring$}
Real-valued tensors $x \in \mathbb{R}^{d_1 \times \dots \times d_k}$ are encoded into the ring $\Zring$ using a fixed-point scaling factor $S = 2^f$ (where $f = 16$ precision bits by default):
\begin{equation}
    \mathsf{Encode}(x) = \lfloor x \cdot 2^f \rceil \bmod 2^{64}, \qquad
    \mathsf{Decode}(\hat{x}) = \frac{\mathsf{Signed}_{64}(\hat{x})}{2^f}.
\end{equation}
Across $N$ parties (typically $N=2$), PriX maintains two secret-sharing representations:
\begin{itemize}
    \item \textbf{Additive Arithmetic Sharing ($\shareA{x}$):} Party $p \in \{0, \dots, N-1\}$ holds $\shareA{x}_p \in \Zring$ such that $\sum_{p=0}^{N-1} \shareA{x}_p \equiv \mathsf{Encode}(x) \pmod{2^{64}}$. Linear combinations $\shareA{x + y} = \shareA{x} + \shareA{y}$ and public multiplications $\shareA{c \cdot x} = c \cdot \shareA{x}$ require zero communication (followed by local or interactive fixed-point truncation).
    \item \textbf{XOR Binary Sharing ($\shareB{x}$):} Party $p$ holds $\shareB{x}_p \in \{0, 1\}^{64}$ such that $\bigoplus_{p=0}^{N-1} \shareB{x}_p = x$. Bitwise XOR ($\oplus$) and bit shifts ($\ll, \gg$) are local; bitwise AND ($\wedge$) requires 1 communication round via binary Beaver triples.
\end{itemize}

\subsection{Multiplication, Truncation, and Nonlinearity Paradigms}
\paragraph{Beaver Multiplication Triples.}
To compute the private product $\shareA{z} = \shareA{x \cdot y}$ (or matrix product $\shareA{X Y}$), the parties consume a pre-generated triple $(\shareA{a}, \shareA{b}, \shareA{c})$ with $c = a \cdot b \bmod 2^{64}$~\cite{beaver1991efficient}. Parties locally compute $\shareA{\epsilon} = \shareA{x} - \shareA{a}$ and $\shareA{\delta} = \shareA{y} - \shareA{b}$, open $(\epsilon, \delta)$ in a single communication round, and evaluate:
\begin{equation}
    \shareA{x \cdot y}_p = \shareA{c}_p + \epsilon \shareA{b}_p + \shareA{a}_p \delta + \mathbb{I}[p = 0] \cdot (\epsilon \delta) \pmod{2^{64}}.
    \label{eq:beaver}
\end{equation}
Because multiplying two $2^f$-scaled integers yields scale $2^{2f}$, the product must be truncated by $f$ bits:
\begin{itemize}
    \item \emph{CrypTen Truncation (\texttt{crypten}):} With two parties, each party arithmetic-shifts its own share by $f$ bits with no communication (local share truncation, as in CrypTen~\cite{knott2021crypten} and SecureML~\cite{mohassel2017secureml}); PriX folds this shift into the compiled Beaver combination. The result is correct up to one unit in the last place, except with probability about $|x|/2^{63}$ for a ring value $x$, when the shares wrap and the result is wrong by a large amount. With more than two parties, CrypTen's masked wrap-count protocol corrects for the wraps $\theta_x$ in one extra round.
    \item \emph{Probabilistic Truncation (\texttt{egk}):} Following Escudero et al.~\cite{escudero2020improved} and Curl~\cite{santos2024curl}, parties mask $\shareA{z}$ with a correlated random pair $(\shareA{r}, \shareA{r \gg f})$, reveal $z + r$, and subtract $\shareA{r \gg f}$ from $(z + r) \gg f$.
\end{itemize}

\paragraph{Five Nonlinear Approximation Backends.}
Table~\ref{tab:modes} summarizes the five approximation modes unified in PriX:
\begin{enumerate}
    \item \textbf{CrypTen Mode (\texttt{mode="crypten"})}~\cite{knott2021crypten}: Approximates $\exp(x) \approx (1 + x / 2^m)^{2^m}$ via $m=8$ repeated squarings, $1/x$ and $1/\sqrt{x}$ via Newton--Raphson iterations, and $\operatorname{GeLU}(x)$ via Taylor-series $\operatorname{erf}(x/\sqrt{2})$.
    \item \textbf{PUMA / Nimbus Piecewise Polynomial Mode (\texttt{mode="poly"})}~\cite{dong2023puma,li2024nimbus}: Evaluates $\operatorname{GeLU}$, $\operatorname{SiLU}$, $\operatorname{Tanh}$, $\operatorname{Sigmoid}$, and $\operatorname{Erf}$ with one batched secure comparison (computing $[\shareA{x} < 0]$ and $[|\shareA{x}| < w]$ in a single carry-lookahead circuit) followed by a degree-4 polynomial on $|x|$, and $\exp$ with a two-piece degree-4 polynomial on $(-5, 0]$ and $[0, 2.5]$ whose pieces share one power basis. No lookup tables are used. The coefficients are least-squares fits over the stated intervals rather than the distribution-aware fits of Nimbus.
    \item \textbf{SHAFT Mode (\texttt{mode="shaft"})}~\cite{kei2025shaft}: Evaluates $\operatorname{GeLU}$, $\operatorname{SiLU}$, $\operatorname{Erf}$, $\operatorname{Sigmoid}$, and $\operatorname{Tanh}$ via a Fourier sine series $\sum_{k=1}^{K} \beta_k \sin(k \omega x)$ whose evaluation takes \emph{1 communication round}: parties reveal $\delta = x - t$ against a pre-shared trigonometric triple $(\shareA{t}, \shareA{\sin(k \omega t)}, \shareA{\cos(k \omega t)})$ and apply the angle-addition identity locally:
    \begin{equation}
        \shareA{\sin(k \omega x)} = \sin(k \omega \delta)\shareA{\cos(k \omega t)} + \cos(k \omega \delta)\shareA{\sin(k \omega t)}.
        \label{eq:shaft_trig}
    \end{equation}
    The series is only accurate within one period, so for $\operatorname{GeLU}$ and $\operatorname{SiLU}$ PriX first computes $[x < 0]$ and $[|x| < w]$ in one batched comparison, evaluates the series on $|x|$, and selects between it and $\operatorname{ReLU}(x)$; the comparison dominates the round count (11 rounds per $\operatorname{GeLU}$ in our measurements).
    For $\operatorname{Softmax}$, SHAFT integrates the differential equation $y'(t) = y(t) \odot (x - \langle y(t), x \rangle)$ over $t \in [0, 1]$ using a fixed number of Forward-Euler steps, without any division, reciprocal, or secure $\max$.
    \item \textbf{Curl Wavelet LUT Mode (\texttt{mode="lut"})}~\cite{santos2024curl}: Builds on wavelet-based function approximation~\cite{gouert2024ripple,reis2025wave}: lookup tables are compressed with Haar and Biorthogonal-2.2 wavelet transforms into coarse coefficient tables, secret-shared lookups are evaluated with one-hot correlated randomness~\cite{santos2024curl}, and Biorthogonal-2.2 tables are interpolated piecewise-linearly after probabilistic truncation $\mathsf{TruncPr}$~\cite{escudero2020improved}.
    \item \textbf{Fission Evaluator Mode (\texttt{mode="fission"})}~\cite{ugurbil2025fission}: Masks and randomly permutes shares before revealing them to a non-colluding plaintext evaluator party, which computes exact float32 nonlinearities and returns fresh secret shares. The evaluator learns the permuted plaintext values, so the security argument relies on the evaluator not colluding with the MPC parties and on partitioning values across evaluators~\cite{ugurbil2025fission}.
\end{enumerate}

\subsection{Threat Model}
\label{sec:threat}
PriX targets the setting of CrypTen and its descendants: $N \ge 2$ computing parties, typically two, that hold additive shares of the model weights and inputs and are \emph{semi-honest}, i.e.\ they follow the protocol but may try to learn from what they see. We assume no collusion between computing parties. Correlated randomness comes from a dealer: either Party~0 itself (\texttt{TFP}, which is only meaningful for benchmarking, since Party~0 then knows every mask) or a separate non-colluding dealer process (\texttt{TTP}). In \texttt{fission} mode, an additional evaluator party sees masked, permuted plaintext values of each nonlinearity's input and must not collude with the computing parties or the dealer; the dealer also knows the permutations. Malicious parties, active attacks, and side channels such as timing are out of scope, as are model-extraction attacks on the revealed output. Section~\ref{sec:security} lists the ways in which the current implementation falls short of even this model.

\subsection{Exact Limb-Decomposed FP64 Matrix Multiplication over $\Zring$}
\label{sec:limb_matmul}
Neither CPU BLAS libraries nor cuBLAS provide 64-bit integer (\texttt{int64}) GEMM, so PyTorch's \texttt{int64} matmul runs on generic unblocked loops. Double-precision GEMM, by contrast, is available in optimized form on both (AVX/FMA on CPU, \texttt{cublasDgemm} on GPU). Note that on the Tesla T4 used in our GPU experiments, FP64 throughput is a small fraction of FP32 throughput and does not use tensor cores.

To compute $C = A B \bmod 2^{64}$ for $A \in \Zring^{M \times K}$ and $B \in \Zring^{K \times N}$ exactly in FP64, we split each unsigned 64-bit entry into $L$ limbs of $w$ bits, $A = \sum_{i} A_i 2^{wi}$ and $B = \sum_j B_j 2^{wj}$. Because only the result modulo $2^{64}$ is needed, every limb pair with $(i + j)\,w \ge 64$ contributes a multiple of $2^{64}$ and can be skipped:
\begin{equation}
    A B \equiv \sum_{(i + j)\,w < 64} (A_i B_j) \, 2^{w(i + j)} \pmod{2^{64}}.
    \label{eq:ten_limbs}
\end{equation}
PriX uses two limb configurations, chosen by the contraction size $K$:
\begin{itemize}
    \item $K \le 512$: $L = 3$ limbs of $w = 22$ bits ($A_2, B_2$ have 20 bits), so only the \textbf{6} pairs with $i + j \le 2$ are computed. Each product entry is below $K \cdot 2^{44} \le 2^{53}$, so every FP64 GEMM is exact.
    \item $K > 512$: $L = 4$ limbs of $w = 16$ bits, so only the \textbf{10} pairs with $i + j \le 3$ are computed. On GPU each pair is a separate slice of one batched GEMM. Each pair product is converted to \texttt{uint64} individually, which is exact for $K \cdot 2^{32} \le 2^{53}$, i.e.\ $K \le 2^{21}$. On CPU, each pair product is likewise converted to \texttt{uint64} before products of equal shift are added, so both backends share the same $K \le 2^{21}$ bound.
    \item $K > 2^{21}$: the contraction is split into chunks of at most $2^{21}$. Each chunk is multiplied exactly as above, and the \texttt{uint64} partial results are added; wrap-around addition is exact modulo $2^{64}$, so the result is bit-exact for any $K$. The chunking is decided at trace time, so it adds no overhead when $K \le 2^{21}$.
\end{itemize}
CrypTen's CUDA backend~\cite{knott2021crypten} uses 3 limbs for $K < 256$ and 4 limbs otherwise, and computes \emph{all} $9$ or $16$ limb products in one batched \texttt{torch.matmul} before discarding the vanishing ones. PriX therefore performs 6 instead of 9 GEMMs for $K < 256$, 6 instead of 16 for $256 \le K \le 512$, and 10 instead of 16 for $K > 512$. On GPU, PriX stacks the surviving limb pairs into one batched GEMM, and the limb extraction, GEMM, conversion, shifts, and modular accumulation are compiled together with the Beaver combination $\shareA{C} + \epsilon \shareA{B} + \shareA{A}\delta + \mathbb{I}[p=0](\epsilon\delta)$. On CPU, CrypTen uses PyTorch's \texttt{int64} matmul directly, so PriX's advantage there comes mainly from using FP64 BLAS.

\subsection{Compiled Set-Propagate-Kill Comparison Circuits}
\label{sec:koggestone}
Private comparisons ($\shareA{x} < 0$, $\operatorname{ReLU}$, $\operatorname{Max}$) extract the most significant bit of a secret-shared ring element by converting $\shareA{x}$ into binary shares with a parallel-prefix carry-lookahead circuit. Like CrypTen, PriX uses a carry-lookahead adder built from set/propagate (Set-Propagate-Kill, SPK) carry signals~\cite{damgard2006unconditionally}, arranged as a Kogge--Stone parallel-prefix tree~\cite{kogge1973parallel} with $\log_2 64 = 6$ rounds. In round $r$ with stride $s = 2^r$, the set and propagate bit-vectors are updated as
\begin{equation}
    S^{(r+1)} = S^{(r)} \oplus \big(P^{(r)} \wedge (S^{(r)} \ll s)\big), \qquad
    P^{(r+1)} = P^{(r)} \wedge (P^{(r)} \ll s),
\end{equation}
where XOR can replace OR because the two terms are never both set. As in CrypTen, both AND gates of a round are opened in one batched binary-Beaver exchange. PriX differs in how the local work is executed:
\begin{itemize}
    \item The dealer generates the binary triples for all 6 rounds in one call (\texttt{generate\_spk\_triples}) instead of one call per round.
    \item The local work between two consecutive openings---applying the previous round's Beaver correction, masking, shifting, and preparing the next round's masked operands---is one compiled kernel (\texttt{\_spk\_step\_fused} in \texttt{circuit.py}). The first and last rounds are fused with the arithmetic-to-binary conversion and with the binary-to-arithmetic conversion of the sign bit, respectively (\texttt{\_a2b\_post\_and\_spk\_round0\_pre}, \texttt{\_spk\_round\_last\_and\_ltz\_b2a\_pre}, \texttt{\_b2a\_combine}).
\end{itemize}

\subsection{Compiled Wavelet LUT Evaluation and Fourier Combination}
\label{sec:lut_shaft_fusion}
In Curl mode (\texttt{mode="lut"}), a nonlinearity such as $\operatorname{InvSqrt}$, $\operatorname{Exp}$, $\operatorname{GeLU}$, or $\operatorname{SiLU}$ truncates the secret input to a table index, reveals the index masked by a one-hot correlation, rotates the one-hot share accordingly, and takes its dot product with the (Biorthogonal-2.2) coefficient tables before interpolating. In PriX:
\begin{itemize}
    \item Each wavelet table is built on first use, placed on the accelerator, and cached for the rest of the session (\texttt{LookupTables(device)}), so table construction is excluded from the timed runs by the warmup.
    \item The rotation and dot product against one table, or against the two Biorthogonal-2.2 tables used for interpolation, are one compiled kernel (\texttt{\_lut\_gather\_dot}, \texttt{\_bior\_lut\_gather\_dot} in \texttt{array.py}).
    \item In SHAFT mode, after the single opening of $\delta = x - t$, the evaluation of Equation~\ref{eq:shaft_trig} for all $K$ terms---computing $\sin(k\omega\delta)$ and $\cos(k\omega\delta)$, scaling them by $\beta_k$, multiplying against the triple shares, and summing---is one compiled kernel (\texttt{\_fourier\_linear\_comb\_jit} in \texttt{approximations.py}).
\end{itemize}

\subsection{Batched Openings and Shared-Memory Collectives}
\label{sec:collectives}
Every private multiplication opens two masked tensors, $\epsilon = x - a$ and $\delta = y - b$. As in CrypTen, both are opened in one round. When $\epsilon$ and $\delta$ have different shapes (e.g.\ $\epsilon \in \Zring^{M \times K}$ and $\delta \in \Zring^{K \times N}$ in a matrix multiplication), PriX passes both to one batched \texttt{all\_reduce}, which writes them back to back into a single shared-memory buffer on the host, exchanges that buffer in one round, and splits the sum.

For multi-process execution on one host, \texttt{InProcessCommunicator} uses a \textbf{4-slot shared-memory ring buffer} (\texttt{multiprocessing.RawArray}) with a 1-byte pipe message as the readiness signal. Each party writes its buffer into slot $\text{step} \bmod 4$, sends the slot index over the pipe, and adds its peer's slot directly from shared memory, without pickling tensors through queues. Each slot holds $2^{21}$ \texttt{int64} values (16\,MiB); larger openings, such as the masked weights of a $768 \times 3072$ linear layer, fall back to a pickled queue transfer. CrypTen instead uses \texttt{torch.distributed} with the \texttt{gloo} backend over loopback TCP. This difference affects every opening, so part of the end-to-end speedups in Section~\ref{sec:evaluation} is due to the communicator rather than to compiled computation. Section~\ref{sec:ablation} measures this share by running PriX over CrypTen's transport.

\section{Researcher Ergonomics and Unified API}
\label{sec:api}
%======================================================================

A central design goal of PriX is enabling cryptography and machine learning researchers to prototype and benchmark private Transformer protocols with minimal boilerplate. Listing~\ref{lst:quickstart} shows a multi-party ablation that evaluates a pre-norm Transformer block under all five approximation modes.

\begin{lstlisting}[style=pythonstyle, caption={Evaluating a private Transformer block under all five MPC approximation modes in PriX.}, label={lst:quickstart}]
import numpy as np
import prix
import prix.nn as nn

class TransformerBlock(nn.Module):
    def __init__(self, d_model=64, n_heads=4, d_ff=256):
        super().__init__()
        self.ln1 = nn.LayerNorm(d_model)
        self.attn = nn.MultiheadAttention(d_model, n_heads)
        self.ln2 = nn.LayerNorm(d_model)
        self.ffn = nn.Sequential(nn.Linear(d_model, d_ff), nn.GELU(), nn.Linear(d_ff, d_model))

    def forward(self, x):
        h = self.ln1(x)
        x = x + self.attn(h, h, h)
        return x + self.ffn(self.ln2(x))

def evaluate_private_block(tokens):
    # Party 0 secret-shares the model weights; party 1 secret-shares the token embeddings
    model = TransformerBlock().encrypt(src=0)
    x = prix.array(tokens, src=1)
    return model(x).reconstruct()

tokens = np.random.randn(1, 16, 64).astype(np.float32)
for mode in ["crypten", "poly", "shaft", "lut", "fission"]:
    out = prix.run(evaluate_private_block, tokens, world_size=2, mode=mode)
\end{lstlisting}

\subsection{Experimental Setup}
We compare \textbf{PriX (JAX)} against a PyTorch \textbf{CrypTen} baseline~\cite{knott2021crypten}: the CrypTen fork that serves as the reference implementation of Curl~\cite{santos2024curl} and Fission~\cite{ugurbil2025fission}. SHAFT's Fourier activations and ODE Softmax~\cite{kei2025shaft}, and the piecewise polynomials of \texttt{poly} mode, are added to this baseline by our benchmark script. The SHAFT functions follow the SHAFT authors' CrypTen-based reference implementation, which computes $\operatorname{GeLU}$/$\operatorname{SiLU}$ with $\operatorname{ReLU}$ followed by a separate range comparison. PUMA and Nimbus have no CrypTen implementation, so the \texttt{poly} functions are ports of PriX's algorithms with the same coefficients, intervals, batched comparisons, and power-basis sharing. Where PriX seeds Newton--Raphson iterations with the limit approximation of $\exp$ regardless of the configured $\exp$ method, the baseline is configured the same way. Both frameworks run 2-party semi-honest protocols with the Trusted First Party (\texttt{TFP}) dealer, $f = 16$ fractional bits, identical inputs, and identical per-mode configuration files (each mode's YAML merged over the framework's default configuration; the two frameworks' default configurations agree on every parameter used). The five modes are:
\begin{enumerate}
    \item \textbf{CrypTen approximations (\texttt{crypten})}~\cite{knott2021crypten};
    \item \textbf{Piecewise polynomials (\texttt{poly})}~\cite{dong2023puma,li2024nimbus};
    \item \textbf{SHAFT Fourier + ODE (\texttt{shaft})}~\cite{kei2025shaft};
    \item \textbf{Curl wavelet LUTs with $\mathsf{TruncPr}$ (\texttt{lut})}~\cite{santos2024curl}; and
    \item \textbf{Fission hybrid evaluator (\texttt{fission})}~\cite{ugurbil2025fission}, with one evaluator process.
\end{enumerate}
We benchmark 10 MPC primitives and nonlinearities ($\text{MatMul } 128\times 128$, $\text{Mul } 128\times 128$, $\text{ReLU } 32\times 64$, $\text{Exp } 32\times 64$, $\text{Reciprocal } 32\times 64$, $\text{InvSqrt } 32\times 64$, $\text{GeLU } 32\times 64$, $\text{SiLU } 32\times 64$, $\text{Softmax } 4\times 32\times 32$, $\text{LayerNorm } 4\times 32\times 64$) and 5 Transformer configurations with sequence length $L=16$: \texttt{BertTiny} (2 blocks, $d=128$, $H=2$), \texttt{BertBase} (1 block, $d=768$, $H=12$), \texttt{GPT2} (1 block, $d=768$, $H=12$), \texttt{Llama} (1 block, $d=768$, RoPE + SwiGLU + RMSNorm, grouped-query attention), and \texttt{ModernBert} (1 block, $d=768$, $H=12$, RoPE + GeGLU). Weights and inputs are random; we measure latency only, not model accuracy.

\paragraph{Methodology.} All parties run as separate processes on one host and communicate through each framework's own local transport (Section~\ref{sec:collectives}); no network latency or bandwidth limit is emulated. Communication rounds and bytes are reported in the transport ablation (Section~\ref{sec:ablation}). Each primitive is run 2 times untimed (to exclude JIT compilation and cache warmup) and then timed 5 times; each Transformer block is warmed up once and timed 3 times. Parties synchronize with a barrier before every timed run, device work is synchronized before the timer stops, and we report the median. Within a platform, all five modes of both frameworks were measured in a single session. CPU experiments use the host listed in Table~\ref{tab:cpu_llm}'s caption. GPU experiments use a Google Colab instance with one NVIDIA Tesla T4. With so few repetitions, differences of roughly 10\% or less between the two frameworks should be treated as within run-to-run noise.

PriX has lower latency than CrypTen in all 75 CPU configurations: Transformer-block speedups range from \textbf{2.83$\times$} to \textbf{9.20$\times$}, and primitive speedups from 1.77$\times$ (Mul, \texttt{crypten} mode) to 20.80$\times$ (Reciprocal, \texttt{fission} mode).
\begin{itemize}
    \item \textbf{Run-to-run noise.} ReLU has the same protocol in every mode, so its spread across modes gives a rough noise estimate. Within this session, CrypTen's ReLU took 22.8--26.8\,ms in four modes and 53.0\,ms in \texttt{fission} mode, where an extra evaluator process competes for the same host. PriX's ReLU took 4.6--5.7\,ms. The CrypTen \texttt{fission} column is therefore likely pessimistic for CrypTen, and the very large \texttt{fission} primitive speedups (9--21$\times$) should be read with this in mind. Across sessions on the same host, identical configurations can differ substantially. Comparing this session with the ablation session of Section~\ref{sec:ablation}, the median Transformer-block latency differed by 4\% and the median primitive latency by 9\%, but 8 of 50 block measurements and 27 of 100 primitive measurements differed by more than 25\%. The largest differences are in CrypTen's \texttt{fission} column (up to 1.7$\times$ on BertTiny, 426.0 vs.\ 249.4\,ms, and up to 2.2$\times$ on primitives), consistent with contention from the evaluator process; the largest outside it is CrypTen's \texttt{lut}-mode ModernBert block (2089.3 vs.\ 1382.5\,ms, 1.5$\times$).
    \item \textbf{Matrix multiplication.} On CPU, CrypTen uses PyTorch's \texttt{int64} matmul, which has no BLAS backend. PriX uses FP64 GEMM on limbs (Section~\ref{sec:limb_matmul}), which explains the 3.9--4.8$\times$ MatMul speedups outside \texttt{fission} mode. Linear layers dominate the $d = 768$ blocks, which is consistent with their larger end-to-end speedups (3.8--9.2$\times$) compared with \texttt{BertTiny} (2.8--4.4$\times$).
    \item \textbf{Comparisons and LUTs.} ReLU is 4.3--5.7$\times$ faster outside \texttt{fission} mode, consistent with fusing the local work of each SPK round. In \texttt{lut} mode, InvSqrt drops from 97.1 to 15.4\,ms (6.33$\times$) and SiLU from 27.3 to 5.2\,ms (5.29$\times$). The transport ablation (Section~\ref{sec:ablation}) attributes about 40\% of the primitive speedups, on a log scale, to the faster local transport; it does not further separate kernel fusion from PriX's other local optimizations.
    \item \textbf{Piecewise polynomials.} \texttt{poly} mode makes GeLU and SiLU cheaper than \texttt{crypten} mode in both frameworks (in PriX, 16.4 vs.\ 40.9\,ms and 15.7 vs.\ 24.3\,ms), but more expensive than Curl's LUTs (5.9 and 5.2\,ms). For $\exp$, the piecewise polynomial is \emph{slower} than the limit approximation (11.5 vs.\ 8.1\,ms in PriX) because its secure comparisons cost more than 8 squarings.
\end{itemize}

\begin{itemize}
    \item \textbf{Run-to-run noise.} As on CPU, CrypTen's ReLU took 44.6--54.0\,ms in four modes and 73.4\,ms in \texttt{fission} mode (with the extra evaluator process); PriX's took 13.7--14.0\,ms throughout. PriX's MatMul was also noticeably slower in \texttt{lut} mode (12.2\,ms vs.\ 3.6--4.9\,ms), where products use $\mathsf{TruncPr}$ rather than the communication-free local shift.
    \item \textbf{Comparisons.} CrypTen's ReLU on the GPU (45--54\,ms outside \texttt{fission} mode) is about twice its CPU time, consistent with many small kernel launches per SPK round. PriX takes 13.7--14.0\,ms, a 3.2--3.9$\times$ speedup.
    \item \textbf{Wavelet LUTs.} In \texttt{lut} mode, InvSqrt drops from 195.5 to 12.1\,ms (16.18$\times$) and LayerNorm from 184.1 to 24.1\,ms (7.63$\times$). Both frameworks use the same single-table Biorthogonal-2.2 configuration. The gain comes from executing the same protocol with fewer launches and a faster local transport, not from a different algorithm.
    \item \textbf{SHAFT and piecewise polynomials.} Fourier GeLU drops from 96.2 to 25.5\,ms (3.78$\times$) and ODE Softmax from 215.8 to 93.7\,ms (2.30$\times$). Piecewise-polynomial GeLU and SiLU take about 32\,ms in PriX, between SHAFT (25--30\,ms) and the \texttt{crypten} approximations (57--76\,ms). As on CPU, the piecewise $\exp$ is slower than the limit approximation (29.6 vs.\ 18.0\,ms).
    \item \textbf{End-to-end.} Transformer-block speedups are smaller on GPU (1.98--3.18$\times$) than on CPU. Plausible causes are the T4's low FP64 throughput and host-side communication, which faster GPU kernels do not reduce. We have not profiled this split.
\end{itemize}

\subsection{Transport Ablation: Where Does the Speedup Come From?}
\label{sec:ablation}
The two frameworks use different local transports (Section~\ref{sec:collectives}), so the speedups above mix two effects: PriX's compiled local computation, and its shared-memory transport. To separate them, we reran PriX with its two-party \texttt{all\_reduce} routed through \texttt{torch.distributed}/\texttt{gloo} over loopback TCP, the same transport CrypTen uses. Everything else in PriX (compiled kernels, limb matrix multiplication, batching, host staging) is unchanged. We checked that this variant produces the same results as the default one. All three configurations (CrypTen, PriX over \texttt{gloo}, PriX over shared memory) were measured back to back on the CPU host of Table~\ref{tab:cpu_llm}, in all five modes, with the communicators' statistics enabled. This was a separate session from Tables~\ref{tab:cpu_llm}--\ref{tab:cpu_ops}, so its absolute latencies differ (the overall Transformer-block geometric mean is 4.39$\times$ here versus 5.05$\times$ over Table~\ref{tab:cpu_llm}); the ablation should be read as a self-contained comparison. Table~\ref{tab:ablation} and Figure~\ref{fig:ablation} summarize the results as geometric means.

\begin{itemize}
    \item \textbf{Most of the Transformer-block speedup remains with an identical transport.} Over \texttt{gloo}, PriX is still 3.24$\times$ faster than CrypTen on Transformer blocks (2.75--4.11$\times$ across modes). The shared-memory transport adds a further 1.35$\times$, about 20\% of the overall 4.39$\times$ on a log scale.
    \item \textbf{The transport matters more for small, round-bound operations.} On the primitives, the transport contributes 1.64$\times$ of the overall 3.39$\times$ (41\%). Their tensors are small, so per-round latency dominates. For ReLU, for example, each run is 9 rounds of under 0.5\,MB in total.
    \item \textbf{Fission mode barely depends on the transport} (1.05--1.08$\times$), because it needs very few rounds between the MPC parties (about 14 per GPT-2 block, versus 98--176 in the other modes).
    \item \textbf{Communication is similar, but not identical.} In \texttt{crypten} mode, the two frameworks' round counts agree to within one round and their byte counts to within 5\% on every Transformer block (e.g.\ 176 rounds and 80.1 vs.\ 79.7\,MB for a GPT-2 block). Two PriX protocol changes account for most of the remaining differences:
    \begin{itemize}
        \item \emph{Smaller comparison openings.} In each carry-lookahead round, one masked vector $P_0$ is ANDed with both $S_1$ and $P_1$. CrypTen first copies $P_0$ to the shape of $[S_1, P_1]$ and therefore masks and opens it twice (its source marks this with a TODO); PriX uses a triple $(a, [b_1, b_2], [a \wedge b_1, a \wedge b_2])$ and opens $P_0 \oplus a$ once, as matrix Beaver triples do for a shared operand. The opened values are still uniformly masked by fresh triples, so security is unchanged. This cuts a comparison from 29 to 23 words per element (ReLU: 0.38 vs.\ 0.48\,MB), and \texttt{poly}-mode blocks send 5--16\% fewer bytes (GPT-2: 88.8 vs.\ 96.4\,MB).
        \item \emph{Batched range tests in SHAFT.} PriX obtains $[x < 0]$ and $[|x| < w]$ from one comparison over the stacked tensor $[x, x - w, -x - w]$, while the SHAFT reference runs two sequential comparisons. This saves 8 rounds per $\operatorname{GeLU}$/$\operatorname{SiLU}$ (11 vs.\ 19) and per SHAFT-mode block (GPT-2: 98 vs.\ 106), at the cost of about 4\% more bytes.
    \end{itemize}
    PriX takes more rounds in two places, both because it applies a configuration setting that the CrypTen code ignores. In \texttt{lut} mode, Curl truncates squares with the communication-free local shift even though the mode specifies $\mathsf{TruncPr}$ for products (its multiplications do use $\mathsf{TruncPr}$); PriX uses $\mathsf{TruncPr}$ for both, so its LayerNorm takes one extra round and each block two (GPT-2: 113 vs.\ 111). In \texttt{crypten} mode, CrypTen's sigmoid sets $\exp$ to 9 squarings in a configuration override that does not enclose the $\exp$ call, so it runs with the default 8; PriX applies the override, so its SiLU takes 25 rounds versus 24 and is about twice as accurate (Section~\ref{sec:accuracy}). Apart from \texttt{shaft} mode, PriX's speedups therefore do not come from fewer rounds.
\end{itemize}
We also recorded the time spent inside communication calls, but for PriX this does not separate cleanly from computation. JAX dispatches device work asynchronously, and the copy to the host at the start of each communication call waits for that work to finish, so compute time is attributed to communication. The transport swap above avoids this problem because it compares end-to-end latencies. This ablation was run on CPU only; on GPU, both transports additionally include device-to-host copies.

No mode is accurate everywhere, and inputs outside a mode's valid range are neither clamped nor flagged:
\begin{itemize}
    \item \textbf{\texttt{lut} (Curl defaults).} PriX uses the same default table ranges as the Curl reference implementation, and they are narrow: $1/\sqrt{x}$ covers only $[0, 2)$, so LayerNorm fails whenever a row's variance is 2 or more; GeLU covers only $|x| < 4$; $\exp$ assumes non-positive inputs and is coarse near 0; $1/x$ and $\log$ are inaccurate near 0.1. None of the 10 softmax runs here failed, but in longer repeated runs about 3--4\% of softmax calls returned some grossly wrong outputs, in both PriX and the Curl reference; we have not yet found the cause. Wider ranges are a configuration change (\texttt{lut\_max\_bits}), at some cost in table size.
    \item \textbf{\texttt{crypten}.} Erf and GeLU use an 8-term Taylor series that diverges for $|x| \gtrsim 3$, as in CrypTen. The Newton--Raphson $1/\sqrt{x}$ loses accuracy near the bottom of its range.
    \item \textbf{\texttt{shaft}.} The Fourier series are periodic, so Sigmoid and Tanh oscillate near the edge of the period ($|x| \approx 8$ by default).
    \item \textbf{\texttt{poly}} stays within about 0.02 on its fitted intervals, and \textbf{\texttt{fission}} is exact to float32 precision (its column shows the median error only).
\end{itemize}
\paragraph{Comparison with the CrypTen/Curl reference.} On identical inputs (10 runs each), PriX is more accurate than the reference implementation on two functions, because of two bugs in the reference code rather than any protocol difference. (1)~CrypTen's \texttt{var()} inverts its \texttt{unbiased} flag and divides by $n - 1$ when asked for the biased variance, so every non-\texttt{fission} LayerNorm output is scaled by $\sqrt{(n-1)/n}$ ($0.9922$ for $n = 64$; a least-squares fit of Curl's outputs gives $0.9921$). Curl's \texttt{lut}-mode LayerNorm has a median error of $5.4 \times 10^{-3}$ versus $4.4 \times 10^{-5}$ for PriX; the bias shrinks with width (about $0.07\%$ at $d = 768$). (2)~The ineffective $\exp$ override described in Section~\ref{sec:ablation} roughly doubles the error of CrypTen's \texttt{crypten}-mode SiLU (median $1.1 \times 10^{-3}$ versus $5.6 \times 10^{-4}$). Neither bug changes the cost of the computation, so the latency comparison is unaffected.
While preparing this evaluation, we found and fixed a bug in PriX's \texttt{fission} mode: when the right operand of a multiplication still carried a deferred truncation, the product was labelled with the wrong fixed-point scale, which made attention scores about $2^{16}$ times too small and attention nearly uniform. The fix changes only the scale label, not the protocol steps that run, so it does not affect the latencies above, which were measured before it. The reference implementations of Curl and Fission in the CrypTen baseline do not have this bug. We have not measured end-to-end model accuracy.

\section{Security Considerations and Limitations}
\label{sec:security}
%======================================================================

PriX is a research framework operating in the \textbf{semi-honest (honest-but-curious)} model, and its current implementation has the following limitations:
\begin{enumerate}
    \item \textbf{Correlated Randomness Providers (\texttt{TFP} vs.\ \texttt{TTP}):} Like CrypTen~\cite{knott2021crypten}, PriX defaults to the Trusted First Party (\texttt{TFP}) provider, in which Party~0 generates the Beaver triples, truncation pairs, and LUT correlations. Party~0 therefore knows the dealer randomness and can recover every secret; \texttt{TFP} is suitable only for performance measurement, and all experiments in this report use it for both frameworks. Setting \texttt{cfg.mpc.provider = "TTP"} runs a separate dealer process (\texttt{TTPServer}) under the usual non-colluding third-party assumption.
    \item \textbf{Pseudorandom Number Generation:} Correlated randomness is currently expanded with \texttt{SplitMix64} (inside compiled kernels) and \texttt{PCG64} (on the host), seeded from OS entropy exchanged at initialization. Neither generator is a cryptographically secure PRF, so a party that observes part of a stream may predict the rest. Replacing them with a keyed counter-mode PRF (e.g.\ Threefry or AES-CTR) is required before PriX can protect real data.
    \item \textbf{Probabilistic Truncation Range:} PriX's $\mathsf{TruncPr}$~\cite{escudero2020improved} is instantiated with parameter $\ell = 62$ in $\Zring$: the opened value is $2^{64-\ell-1}(x + 2^{\ell-1} + r)$ with a uniform $\ell$-bit mask $r$ and a masked carry bit. The opening hides $x$ regardless of its value; the range condition $|x| < 2^{\ell-1} = 2^{61}$ on the ring integer is needed for \emph{correctness}. With $f = 16$, this means real values below $2^{29}$ in magnitude for products at precision $2f$, and below $2^{45}$ for values at precision $f$. Values outside this range give incorrect results without any error being raised. As usual, the truncated result may be off by one unit in the last place.
    \item \textbf{Implementation Hardening:} The multi-host transport exchanges pickled Python objects, the \texttt{TTP} dealer dispatches requests by method name without an allowlist, and cached lookup tables in the temporary directory are not integrity-checked. Each lets a malicious peer or local user execute code or corrupt results, which is outside the semi-honest model but matters for any deployment.
    \item \textbf{Evaluation Scope:} All measurements are single-host, with no network emulation; they characterize computation and local inter-process overhead, not wide-area deployment. The two frameworks also use different local transports (Section~\ref{sec:collectives}). We quantify this on CPU (Section~\ref{sec:ablation}) but not on GPU. We report the accuracy of individual nonlinearities (Section~\ref{sec:accuracy}) but not end-to-end model accuracy. PriX has been tested on CPUs and CUDA GPUs only. On TPUs, its FP64 limb matrix multiplication would rely on emulated double precision.
\end{enumerate}

\section{Related Work}
\label{sec:related}
%======================================================================

\paragraph{MPC frameworks for machine learning.} CrypTen~\cite{knott2021crypten} is the PyTorch framework on which Curl, Fission, and our baseline build. MP-SPDZ~\cite{keller2020mpspdz} compiles programs for a large set of MPC protocols and security models, but targets general computation rather than tensor workloads. The closest system to PriX is SecretFlow-SPU~\cite{ma2023spu}, which also compiles machine-learning programs (including JAX) through XLA: SPU lowers the whole program to its own IR and executes it with a C++ runtime over several protocols, whereas PriX stays in Python, compiles only the local phases between openings with JAX itself, and aims at fast prototyping of CrypTen-style approximation methods. PUMA~\cite{dong2023puma} is implemented on SPU.

\paragraph{GPU acceleration.} CryptGPU~\cite{tan2021cryptgpu} runs CrypTen-style 3-party protocols on GPUs and introduced the floating-point limb decomposition for ring matrix multiplication that CrypTen's CUDA backend uses; PriX refines it by computing only the limb products that survive modulo $2^{64}$. Piranha~\cite{watson2022piranha} is a general GPU platform for secret-sharing MPC, and SIGMA~\cite{gupta2024sigma} evaluates GPT models on GPUs with function secret sharing.

\paragraph{Private Transformer inference.} Besides the methods PriX implements~\cite{santos2024curl,dong2023puma,li2024nimbus,kei2025shaft,ugurbil2025fission}, two-party systems combining homomorphic encryption with secret sharing, such as Iron~\cite{hao2022iron}, BOLT~\cite{pang2024bolt}, and BumbleBee~\cite{lu2025bumblebee}, target the client--server setting with lower communication, and MPCFormer~\cite{li2023mpcformer} replaces nonlinearities with MPC-friendly ones and recovers accuracy by distillation. These are complementary: PriX's contribution is an execution engine for secret-sharing protocols, not a new approximation or protocol.

\section{Conclusion}
\label{sec:conclusion}
%======================================================================

We presented \textbf{PriX}, a JAX/XLA framework for privacy-preserving Transformer research via Secure Multi-Party Computation. PriX implements five MPC approximation paradigms (\textbf{CrypTen}, \textbf{piecewise polynomials}, \textbf{SHAFT}, \textbf{Curl}, and \textbf{Fission}) behind one API. It compiles the local steps of each protocol with XLA, computes only the surviving limb products in its exact FP64 ring matrix multiplication, and uses a shared-memory local transport. On a single host, it has lower latency than the PyTorch CrypTen baseline in every configuration we measured, with Transformer-block speedups of \textbf{2.83$\times$--9.20$\times$} on CPU and \textbf{1.98$\times$--3.18$\times$} on a Tesla T4 GPU. With an identical transport, PriX is still 3.24$\times$ faster on Transformer blocks (geometric mean, CPU); the shared-memory transport accounts for the remaining factor of 1.35$\times$. Evaluating over real networks, measuring end-to-end model accuracy, widening the default Curl table ranges, extending the transport ablation to GPU, and replacing the non-cryptographic PRNGs are the main next steps. PriX is open-source and available on PyPI via \texttt{pip install prix-jax}.
